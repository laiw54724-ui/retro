# P2 production writing: exact outstanding compatibility blocker

Status: proposed minimal code follow-up; **not implemented** in reader #91 or writer #94. Reader #91 stays at reviewed 879961d6d834dd668944afd97e9da2ac89071bae. Writer #94 is ready for local functional review only. Its production gate is hard off (`import.meta.env.DEV` must also be true), so even VITE_APPEARANCE_P2_WRITER=true cannot enable a production build. Reader deployment alone is insufficient.

## Evidence in the current routes

`apps/api/src/routes/sites.ts` PUT /api/sites/:siteId/draft reads only id,draft_version, checks expectedVersion, and replaces draft_document. A client which has stripped appearance fields but has the current version can submit a valid old-shape document. Optimistic concurrency prevents races; it does not establish preservation capability. `apps/web/src/lib/api.ts` sends expectedVersion/document only. GET /api/sites/:siteId advertises no write-compatibility contract. No old/stale-client exclusion exists in #91/#94. Manual tab refresh, cache clearing, or deployment timing is not an enforceable exclusion mechanism.

## Required minimal API/client change before production enablement

Use a narrow **transport** capability, not a document schema/version redesign. The exact proposed contract is `clientAppearanceContract: 1` in draft/create request bodies and `clientAppearanceContract=1` in import preview/confirm query parameters. A constant body/query field avoids adding CORS headers or changing auth/permissions. This is a cooperative data-preservation protocol, not a security credential. Only a client build verified against the extended readers/adapters/roundtrip tests may send it, regardless of whether its author controls are enabled.

1. Add a pure raw-document predicate which detects P2 dependence: theme.appearance is present, any new window color key is present, or a present window.appearance is partial (missing legacy required titleFrom/titleTo). Check property presence, including an empty theme.appearance and explicit false titleGradient; do not rely on truthiness or parsed defaults. Preserve the absence of inherited values. Use raw input before any lossy parsing, and inspect the stored canonical document too.
2. Extend SaveDraftSchema's transport envelope with optional clientAppearanceContract literal 1. In the draft route's existing snapshot read, include draft_document. After normal authentication/access and validation, if **stored OR incoming** document depends on P2 and the request lacks the exact capability, reject with HTTP 426 / `client_upgrade_required`, with zero writes. A stripped incoming document must not bypass the check because the stored document still contains the fields. If the existing version is stale, existing 409 version_conflict may take precedence; either way no write occurs.
3. Keep the existing `.eq("draft_version", expectedVersion)` compare-and-swap. If an old save reads a legacy vN while a capable client adds P2 at vN+1, the old save's conditional update must fail. Do not split preservation checks from the versioned snapshot or remove the CAS. A capable client is allowed to intentionally reset/delete fields; do not blindly merge missing fields back, since that would break reset/delete semantics.
4. For POST /api/sites, require the same body capability when raw incoming data depends on P2. For POST /api/imports/preview and /confirm, require the query capability for **all imports** once this protocol is deployed: an old client may strip fields before sending a package, so looking only for surviving P2 keys is insufficient on this input path. Keep the existing preview digest and all import validation. Do not alter the portable export package or store capability fields in documents. Old import clients receive upgrade-required rather than silently creating a lossy copy.
5. GET /api/sites/:siteId must advertise a top-level `writeCompatibility: { appearanceP2: 1 }` only from the API version which implements these guards. Use no-store/fresh authenticated responses. The web client must combine this per-load server advertisement with the existing build flag before showing production writer controls; missing/unknown advertisement means writer hidden. `api.saveDraft` must send the capability from the verified compatible client even with the authoring flag off, allowing such clients to preserve/edit P2-bearing documents normally.
6. Handle `client_upgrade_required` explicitly in EditorPage: pause autosave/publish, preserve local unsaved state, show a localized upgrade/reload action, and require a fresh canonical reload before retry. Do not retry with a marker merely to bypass rejection, overwrite the stored document, or discard the user's pending text. The server rejection is the protection; the reload action is recovery UX. Add only scoped four-language copy.
7. Existing server-only publish, publish/retry and asset-migration routes use stored canonical documents rather than client document payloads. Deploy their compatible readers/projection/rewrite functions and prove all P2 fields survive them; audit that no alternative document-replacement route bypasses the guard. No migration should be executed by this follow-up task.

This belongs in a small separately reviewed API/client code PR, stacked after the appearance reader/writer contracts. Expected files: apps/api/src/lib/site.ts, an appearance-preservation helper and focused route tests, routes/sites.ts, routes/transfer.ts, web lib/api.ts, EditorPage.tsx, the writer gate/controls' per-load wiring, scoped locale keys and tests. No database migration, auth/permission/CORS changes, global schema-version change, generic capability registry, or broader content redesign is needed. The existing reader head must not be amended to sneak in this policy.

## Required proof and rollout order

- Deploy guarded compatible API first; ordinary legacy docs may still save without the marker, but protected documents and all imports cannot be submitted by unverified clients. Verify the exact deployed API build exposes the contract and rejects incompatible requests before any P2 document is introduced.
- Deploy verified compatible web readers/senders with production author controls still off. The current #94 hard-off gate is removed/replaced **only by the reviewed follow-up which implements the complete handshake**, not by an environment-only change.
- Test a frozen old client using the current expectedVersion and a document with all P2 fields stripped: HTTP 426 and byte-for-byte stored document unchanged. Test stale version racing a first P2 write: no overwrite. Test an absent/malformed/unsupported marker, a valid marker with invalid schema, a capable intentional full reset, and unaffected legacy-document saves. A marker is not auth; existing access checks remain mandatory and arbitrary callers can intentionally author data, so claims are limited to excluding known incompatible clients rather than adversarial tamper-proofing.
- Test missing/unknown server advertisement keeps production controls hidden, compatible flag-off clients preserve P2 data, and upgrade errors halt retry without dropping local edits. Test old import preview/confirm rejection even if their submitted package has already lost P2 fields.
- Record exact deployed API/web SHAs and end-to-end save/reload, publish/public projection, owner/public export/import, v2→legacy editing, and stored-field reset canaries. Then a separately approved build may enable controls using both the flag and advertised contract.
- After new writes, never roll API/readers below the preservation guard or P2 readers. Disable author controls while retaining compatible readers/guard, preserve backups and fix forward. An old-reader rollback/data downgrade requires separate reviewed data work.

Until this code and deployment evidence exist, #94 remains **not production-enableable**. Local mocked tests establish functional behavior, not server enforcement or deployment compatibility.
